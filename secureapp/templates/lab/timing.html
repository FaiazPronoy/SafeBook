How long it took is an answer too

A verifier that stops at the first wrong byte takes longer when more of the guess was right. That is enough to find a 32 byte MAC one byte at a time, without ever guessing the whole thing. The loop leaks, plainly

It climbs straight up with the number of correct bytes, because it does one Python comparison per byte and returns at the first mismatch. An attacker tries all 256 values for byte one, keeps the slowest, and moves on. That is 8192 attempts to forge a MAC, instead of 2256.

== is not the interesting case here

Comparing two bytes objects in CPython drops into memcmp, which reads several bytes at a time in C. Over 32 bytes the whole comparison is faster than the loop that calls it, so the difference is buried in noise — on this run, a spread of {{ eq_spread|floatformat:0 }} ns against the loop’s {{ loop_spread|floatformat:0 }} ns. That is a measurement failing to find something, not proof it is safe: the same code on longer data, or in another runtime, has no such cover.

So SafeBook uses hmac.compare_digest. It always reads every byte, whatever it finds. It costs nothing and it removes the question — which is the right trade when the alternative is arguing about whether a leak is small enough to ignore.
